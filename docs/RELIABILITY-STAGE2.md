# 阶段 2：采集与投递边界回归

本批仅在一次性测试数据上执行故障注入，不调用真实来源、模型或 SMTP。不是完整阶段 2 或生产验收。

## 已复现并修复

- **无启用来源的本地采集误报成功**：现在以失败结束，不触发抓取，释放运行槽并记录完成时间。来源配置修复后可再提交任务。
- **计划日报运行跨当地午夜仍入队投递**：原逻辑只在开始时检查计划日期。现在在最终提交事务、租约校验后再次按任务保存的时区与日期检查。超期不创建投递项，任务明确失败；已采集数据、已生成 brief 与 checkpoint 保留，不自动再次调用模型。手动日报不附带计划日期，仍可正常完成。

回归覆盖 UTC/Asia-Shanghai 当地跨日、UTC 跨日而当地不跨日、send 开关、手动任务，以及已完成 brief 的过期任务不重新生成。修复前两个跨日回归实际失败（错误状态 succeeded），修复后通过。

## 仍需推进

- **租约丢失的采集记录**：已离线复现主 Run 恢复后，其旧 FetchRun 仍为 running。需增加采集记录与主任务/attempt 的关联，由有权恢复的事务终结旧记录，并覆盖进程崩溃；不能靠失去租约的 worker 绕过 fence 修改来源状态。后续 0010 补丁已实现新尝试关联恢复，见下节；历史无关联行仍不能猜测归属。
- 日期检查防止过期任务新建 outbox；已经按时入队、等待审核或重试直到次日的投递仍需单独定义过期政策。
- 真实来源可用性、供应商/邮件 canary、生产数据恢复未验收。

已有 PR26 的隔离 Docker SQLite/PostgreSQL smoke 覆盖镜像、容器间 HTTP、Worker 和重启数量保留；不覆盖宿主机端口发布或用户电脑。

## 采集租约恢复补丁（0010）

新 durable 采集记录在首次写入时保存主任务 ID 与本次 lease token，并仍由同一 fence 保护提交。恢复者赢得主 Run 的条件更新后，在同一事务中只把该 run/token 下仍 running 的 FetchRun 标为 interrupted，记录完成时间与脱敏原因。不会改动来源健康、已成功证据、其他尝试或已终态采集。事务失败同时回滚主任务与采集状态。

故障注入覆盖旧抓取晚返回成功/失败、新尝试先成功、两个恢复者竞争、进程崩溃重试/耗尽预算，以及恢复事务中途失败。0010 的 SQLite 带数据升级→降级→升级验证旧中文记录与外键；PostgreSQL CI 运行同一并发恢复测试及迁移往返。

升级前停止旧 API/Worker 并备份。0010 的关联列可空；旧版与非 durable 采集没有可靠 owner，不能猜测归属，因此不会自动标记历史孤立记录。该修复保证新关联尝试的接管清理，不保证取消已在途的网络请求，不绕过旧 worker 的 fencing。降级会移除新增关联信息，只在可丢弃测试库验证，不能用于生产回滚承诺。
